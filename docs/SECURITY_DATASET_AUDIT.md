## Confirmed findings

### 1. IP shortcut and a documentation discrepancy

Existing protocol reports 48,894 phishing IP hosts and zero legitimate IP hosts. Reused `subdomain_audit.parse_hostname` and `is_ip_address` to stratify the new cohorts: confirmed those counts (77.0081% of phishing rows).

A targeted check of stored `has_ip_address`, necessary to reconcile the protocol's 77.04% baseline recall, finds **48,916**, not 48,894, phishing positives and zero legitimate positives. Row-level reconciliation (evidence `ip_flag_vs_parsed`): both definitions agree on **48,894** rows, **22** rows are stored-only (`has_ip_address=1` but strict parsed hostname is not an IP), and **0** rows are parsed-only. The 22-record discrepancy is therefore fully accounted for at row level. The protocol's baseline uses stored flags, whereas its hostname finding uses parsed hosts. Do not silently conflate the two definitions. Resolve the 22 stored-only rows with the feature owner; this audit does not overwrite flags.

High IP-only accuracy is dataset-specific, not evidence that IP hosting implies phishing. Host-group splitting does not remove a shortcut present in both partitions.

### 2. Negative subdomain cohort is not simply malformed URLs

All **1,308** rows with `subdomain_count=-1` are phishing (2.0601% of that class). Of these:

- 1,300 have both `tld_length=0` and `domain_name_length=0` (intersection `zero_tld_and_zero_domain_name_length=1300`; overall `both_zero=1300` in evidence `zero_length_bundle`).
- The remaining 8 have both lengths equal to 5.
- No parsed host is a strict IP address (`strict_ip_hosts=0` in evidence).
- Only one has a missing host: the dataset sentinel `Offline`.
- Nine have a single-label host by this audit's definition.
- Therefore 1,307 have an extracted host; extracting a host is not validating a URL.

The cohort includes ordinary-looking multi-label hosts and a long deceptive brand-like hostname (see JSON). Treating -1 as a literal subdomain quantity or rejecting the entire cohort as malformed is unjustified.

**Hypothesis, not confirmed:** a source-specific parser failure or missing-value convention could produce the correlated -1/zero-length bundle and become a label shortcut. The original extractor/source metadata are needed to distinguish this from a deliberate definition. Existing simple label-count audits cannot establish original intent.

### 3. Host concentration is strongly asymmetric

Using the existing subdomain helper (which excludes `Offline`), phishing has 26,887 unique extracted hosts; legitimate has 37,114. The top ten phishing hosts account for **7,660 rows (12.0645%)**, compared with **252 (0.6742%)** for legitimate. Denominator for both percentages is **all rows in the class** (63,492 phishing / 37,380 legitimate), including the 1 phishing row with a missing host; evidence also records `top10_percent_of_parsed_host_rows` (12.0647% phishing) for comparison. Exact top hosts and counts are in the evidence JSON; names are dataset observations, not claims about current sites.

The protocol's 64,001 total hosts differs from this parser's total because the host-split parser accepts `Offline` as a hostname. Parser definitions must be unified before interpreting group boundaries. The protocol also reports only github.com shared between classes; that is prior evidence, not a newly repeated cross-class audit.

**Hypothesis:** repeated campaigns or collection sources may dominate phishing. No source, campaign, capture-time or provenance field exists in the cleaned columns, so source dominance and collection leakage cannot be confirmed from hostname frequencies alone. Nor are counts by full host equivalent to counts by registrable domain.

### 4. Structural cohorts differ by label

| Indicator | Phishing count (% of class) | Legitimate count (% of class) |
|---|---:|---:|
| URL >=200 characters | 89 (0.1402%) | 0 (0%) |
| Percent-encoded byte marker | 557 (0.8773%) | 13 (0.0348%) |
| Literal query marker `?` | 758 (1.1939%) | 38 (0.1017%) |
| Backslash | 48 (0.0756%) | 0 (0%) |
| Whitespace | 5 (0.0079%) | 0 (0%) |
| Literal `@` anywhere | 4 (0.0063%) | 1 (0.0027%) |
| Non-ASCII | 0 | 0 |
| Non-IP host with >=5 dot-separated labels | 256 (0.4032%) | 499 (1.3349%) |
| Hyphen in host | 1,800 (2.8350%) | 2,780 (7.4371%) |

A literal `@` is not necessarily userinfo. Deep hosts/hyphens are more prevalent in the legitimate class here, contradicting simplistic universal suspiciousness rules. Backslashes/whitespace are suspicious parser-differential markers, not a complete malformed-URL census. No definitive overall malformed percentage is claimed.

**Risk inference:** rare query strings, encoding and absent Unicode suggest weak coverage of difficult modern inputs. We have no representative external sample, so actual real-world coverage or error rates remain unknown. Dataset labels are accepted for analysis, not independently verified.

## URL cases and automated coverage

`tests/cases/url_security_cases.json` supplies 28 synthetic, offline cases covering normal URLs, documentation IPv4/IPv6, nested hosts, digits/hyphens, queries, a synthetic shortener, redirects, encodings, userinfo, fragments, case/trailing dots, schemeless/protocol-relative input, IDN/punycode, missing/non-string/sentinel input, broken brackets, bad ports, backslashes, encoded hosts, integer/leading-zero IPs, controls and unsupported schemes. Examples use reserved example names or documentation IP ranges; no real shortener is contacted.

Each entry separates **observed existing-helper hostname/IP expectations** from **proposed production behavior**. These are not phishing/legitimate ground-truth labels. A syntactically normal URL is not automatically legitimate.

`tests/test_url_security_cases.py` calls existing audit helpers only, including their preliminary non-PSL subdomain function. Socket access is blocked in `setUp` for every test. Tests characterize actual helper behavior; passing them is not approval of all behavior. For example, the helper accepts an out-of-range port's host, strips newline via urlsplit, and returns percent-encoded hosts without validating them. Production should explicitly handle these cases rather than inherit them accidentally.

Coverage now includes: characterization of hostname/IP and preliminary subdomain helpers, a determinism test that asserts repeated calls match the documented expected host/IP and subdomain values (not a self-comparison), missing/non-string/sentinel input handling, normalization (case, trailing dot, whitespace, schemeless, protocol-relative, userinfo), and a cases-file integrity check (28 cases, unique ids, required keys/types). The audit itself validates required columns (`URL`, `ClassLabel`, `subdomain_count`, `tld_length`, `domain_name_length`, `has_ip_address`), labels (0/1 only, both classes required so class percentages are never NaN), and URL types before running, reports URL types in `url_type_audit`, and handles missing/non-string URLs safely as missing host / empty text instead of raising. Host parsing goes through `_safe_parse_hostname` so the audit never passes raw non-string values to `parse_hostname` directly.

Run outcome: **9 test methods passed; 1 production-contract method explicitly skipped**. The parameterized hostname method exercises all 28 cases. No production feature extractor assertions are represented as complete.

## Implementation risks observed in source

- `src/phishx/features/__init__.py` has no shared extractor interface. Several audit scripts use differing parsing definitions.
- `app/main.py` imports `safe_hostname` and `extract_basic_signals` from `app/utils/url_helpers.py`, but importing `app/main.py` executes Streamlit UI code. It is not a stable shared feature API.
- App helpers prepend `http://` to protocol-relative input, losing the intended hostname.
- `extract_basic_signals` calls `.strip()` before its try block; None and integers can raise AttributeError. It also emits signals for empty input instead of an explicit invalid status.
- Accessing `.hostname` alone does not validate port ranges, controls, allowed schemes or DNS labels. Python urlsplit behavior is not equivalent to browser navigation.

These app observations are source-review findings, not completed production integration tests. App code was restored to pre-merge `main` (`e09013c`) to remove duplication; no UI or logic change was introduced by this audit.

## Recommendations

1. Keep the shared dataset immutable. Document negative sentinels and original feature definitions before deciding any remediation with the team.
2. Retain the fixed host-group evaluation; add reported slices for IP/non-IP, negative-subdomain rows, query/encoding cohorts and repeated-host concentration. Include confusion matrices, phishing precision/recall/F1, legitimate false-positive rate, sample counts and uncertainty, not only accuracy.
3. Have the model owner run controlled feature ablations for stored IP flags, -1/zero-length bundle and tld_popularity, fitting all preprocessing on train only. These are proposed experiments, not results.
4. Consider an additional offline, pinned-PSL registrable-domain/campaign split: distinct subdomains can share ownership or campaign infrastructure despite zero exact-host overlap. Do not replace the agreed fixed split unilaterally.
5. Obtain source/license/capture-date/label-method metadata; assess temporal and campaign holdouts. Hostnames alone cannot establish source provenance or current ground truth.
6. Build a separate reviewed challenge set, including benign IP-hosted services, benign long/query-heavy URLs, Unicode and domain-hosted phishing. Never insert synthetic adversarial examples into the shared labeled dataset without review.
7. Establish one shared HTTP(S) input contract, explicit invalid/missing status, strict IP rules, ambiguity policy, Unicode normalization and deterministic raw-vs-normalized feature definitions. Never return a confident benign prediction just because extraction failed.
8. Keep parser testing network-free. Shortener destination safety is unknowable from lexical structure alone; do not follow redirects to obtain labels.
